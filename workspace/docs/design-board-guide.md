# Stage 3.0 — File-native Visual Game Studio

## Why this architecture

The previous stages established GDD rules, executable game acceptance, and a
bounded Agent repair loop. Stage 3.0 adds a visual editor over **the same
workspace files**, rather than inventing a second private database of scenes
that Agents cannot inspect.

Design Canvas is an additive project artifact, not a replacement for
game.design.json or scripts/game.js. The editor lives next to the existing
Game Preview, so users can compare the conceptual model and actual running
game. A read-only, capped Git diff provides code context.

## Source of truth and API

- design.board.json — v1 JSON graph document (tracked alongside other game files)
- Nodes: stable IDs, scene/mechanic/note/asset kind, title, description, x/y,
  width/height, and optional reference.
- Edges: stable IDs, source ID, target ID and display label.
- Mechanic nodes generated for a new board preserve GDD mechanic IDs
  in reference fields; board node IDs are stable and unaffected by GDD
  ordering. The document remains editable without GDD.
- Asset nodes contain **workspace-relative references**, not inline data,
  code, absolute paths, or remote URLs. The current editor lists existing
  assets; embedding/raster artwork is deferred to Stage 3.1.
- GET /api/design-board/<sessionId> returns board, revision SHA-256, GDD
  mechanic metadata, safe asset inventory and bounded code diff.
  GET never implicitly writes a board file.
- PUT accepts board and expected revision. The server strictly validates
  IDs, geometry, references, edge endpoints, caps and file sizes.
  The route requires a session capability and matching Origin.
  Updates are compare-and-swap with exclusive local lock and atomic rename.
  A stale revision returns HTTP 409; it never silently overwrites.
  Reload explicitly discards local unsaved edits.

## UX

- Game Preview / Design Canvas tabs share a session.
- Canvas node types: scene, mechanic, note and asset.
- Add, select, drag and inspect nodes. Add/remove directed connections.
- Property inspector edits titles and descriptions on blur.
- Undo/redo keeps up to 50 local snapshots, and clear redo on branch edits.
- Explicit Save, dirty indicator and conflict warning.
- Read-only Code diff tab (working tree changes in scripts/game.js).
- Responsive layout: node inspector docks beneath the board on smaller widths.

## Constraints

Max 64 nodes and 128 edges; max 128 KB serialized board.
Node title max 100 chars, description max 1200 chars.
All IDs follow a fixed identifier syntax, and asset references are limited
to safe workspace assets/ filenames. No eval, HTML execution, arbitrary URLs
or user-supplied filesystem paths are accepted in a board file.

Local atomic CAS guards simultaneous writes on one filesystem, but cannot
promise full multi-node transactions, presence, or collaborative editing.
The current React history is client-local only. Stage 3.1 can build an asset
pipeline; Stage 4.x should introduce durable server-side leases/audit for
multiple workers. The board does not manipulate game.js automatically.
Agents can inspect or edit the board file through existing workspace tools,
but any stale browser save will be rejected.

## Test acceptance

- Schema accepts round-trip board files and stable GDD references.
- Undo/redo covers creation, movement, edge changes and deletion.
- Duplicate IDs, dangling edges, scripts and unsafe references are rejected.
- GET derives GDD-first initial board without disk mutation.
- PUT detects stale writes and prevents symlink escapes.
- Same-origin + session capability checks block unauthorized mutations.
- Next.js typecheck, lint, unit tests, production build and Chromium
  regression tests pass before PR review.

Not yet included: multiplayer/collaboration, auto-merge, asset transformation,
direct scene->game compiler, visual screenshot regression or visual game physics
editing. Browser-based Game Preview remains generated by the existing pipeline.
